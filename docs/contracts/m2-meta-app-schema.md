# Registro global de App Meta — etapa de banco

A migração 00007 cria `meta_app_registry` (`id`, `app_id`, `status`, `created_at`) e `meta_app_registry_secrets` (`registry_id`, `key_version`, `ciphertext`, `aad_scope`, `aad_tenant_id`, `aad_entity`, `aad_entity_id`, `aad_field`, `aad`). O UUID e os valores são copiados das tabelas legadas; colisões de UUID entre tenants ou AAD legada incompatível fazem a migração falhar atomicamente. Nenhum segredo é recifrado e nenhuma chave mestra é usada pelo SQL.

Para `legacy_tenant`, o serviço futuro deve reconstruir o contexto confiável a partir das colunas: tenant = `aad_tenant_id`, entidade = `meta_app`, ID = `aad_entity_id` (igual a `registry_id`) e campo = `app_secret`. Deve comparar a AAD armazenada com esses quatro componentes em texto separados por byte 0x1f e usar esse contexto e `key_version` para autenticar e abrir o ciphertext. Para `ingress_registry`, o contexto é `ingress_registry`, `meta_app_registry`, UUID do registro, `app_secret`, separados por 0x1f; `aad_tenant_id` é nulo. Esses valores são estabelecidos pelo servidor, nunca pelo cliente.

As tabelas globais têm FORCE RLS e acesso exclusivo a `chatisp_ingress` com `app.access_scope = ingress`; app e platform não recebem privilégios. As tabelas, FKs, isolamento e unicidade de `meta_apps.app_id` legadas permanecem. O serviço atual ainda escreve apenas no legado, portanto a cópia global não é sincronizada. B8-02 permanece pendente: a migração 00008 e o serviço coordenado devem tratar sincronização e remoção da unicidade legada antes de permitir múltiplos tenants por App ID. A reversão 00007 falha atomicamente se uma linha global não corresponder à cópia legada, evitando descarte silencioso de dados globais novos ou alterados.
